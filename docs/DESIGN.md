# ANTI-AIR 設計文件

版本 0.1 ／ 2026-08-17

---

## 1. 這份設計改了什麼

原始構想的方向判斷是對的：涵蓋不是圓、高度滑桿是核心互動、參數要帶不確定度。
以下六項是本次重新設計後不同的決定，每一項都附理由。

| # | 原構想 | 改為 | 為什麼 |
|---|---|---|---|
| 1 | `R_eff(h) = min(R_kin, R_horizon, R_terrain)` 三者取最小 | **MVA 場**：把曲率、折射、地形壓成同一個純量場；運動學射程另外處理 | 三者取 min 是錯的合成方式。地形遮蔽不是一個「距離」，是逐方位、逐距離的高度門檻，取 min 會把山後的分離可視區整個抹掉 |
| 2 | viewshed 太重，必須離線預算成 raster tiles | **在 Web Worker 中即時算**，實測 720×500 取樣 **22.8 ms** | 一算就得到所有高度切片。離線預算會直接殺死「拖曳陣地看變化」，而那才是這個工具的價值 |
| 3 | 推薦 CesiumJS 做 3D | **MapLibre GL + 自訂 WebGL2 圖層，2D 優先**；3D 只做垂直剖面 | 多個 3D 包絡體疊起來是視覺糊團，看不出縱深。剖面圖的資訊密度高一個量級 |
| 4 | 幾何運算轉 TWD97 / EPSG:3826 | **不投影**，直接在橢球上用大地線正算 | 3826 分帶對本島夠用，但東沙、太平島、東引超出後誤差爆掉，而海基兵力正是要討論這些 |
| 5 | 涵蓋 = 能不能打到（面積） | **接戰機會 = 能打幾次**（時間） | 面積回答「能不能」，時間回答「來不來得及」。對 250 m/s 的低空巡弋飛彈，這兩個答案經常相反 |
| 6 | `range_at_alt` 單一插值表 | 拆成 **運動學包絡 / 偵測距離（RCS 相依）/ 導引 LOS 需求** 三條獨立鏈 | 原本把「飛得到」和「看得到」混成一個數字。RCS 0.1 m² 與 5 m² 的偵測距離差 2.7 倍，這是低空巡弋飛彈能突防的主因 |

## 2. 核心觀念：從涵蓋面積到接戰機會

一張防空涵蓋圖最常見的誤導，是它回答了「這個點在不在射程內」，
卻沒回答「當威脅飛過這個點時，防空系統來不來得及打」。

對一條給定航跡，實際能打幾次是：

```
T_window  = t_離開包絡 − max(t_進入包絡, t_偵獲 + t_反應)
N_shots   = min( channels, floor( T_window / (t_flyout + t_assess) ) )
t_flyout ≈ r / v_missile
```

`t_偵獲` 由 MVA 場決定，`t_進入包絡` 由運動學包絡決定，兩者往往不同時發生 ——
**在山區，經常是威脅早已進入射程，但還沒被看到**。這個時間差就是低空走廊的本質，
而任何只畫面積的工具都表達不出來。

所以本專案的主輸出有兩層：

- **幾何層**（高度切片、縱深熱圖）：回答「哪裡有洞」
- **時間層**（接戰時間軸、射擊機會數）：回答「這個洞有多致命」

## 3. MVA 引擎

### 3.1 定義

對每個感測器 / 發射器陣地，計算一張極座標場：

```
MVA(φ, r) = 位於方位 φ、距離 r 的目標，必須飛到多高才能被本站直視
```

計算方式是沿每條方位射線由近至遠推進，維護「到目前為止的最大視仰角」`θmax`：

```
θ(r')      = atan( (z(r') − c(r') − h_site) / r' )      # 地形點的視仰角
θmax(r)    = max over r' ≤ r of θ(r')
MVA(φ, r)  = h_site + r·tan(θmax) + c(r)
c(r)       = r² / (2·k·Re)                              # 曲率 + 折射下沉
```

`k = 4/3`（標準大氣有效地球半徑因子），`Re = 6371008.8 m`。

### 3.2 為什麼這個式子是對的

`θmax` **允許為負**。居高臨下望海時它就是負的，這正是雷達地平線比水平視線更遠的原因。
平坦海面上，`θmax` 的極值出現在 `r = √(2·k·Re·h_site)` 處（切點），代入後可解析地還原教科書公式：

```
d(km) = 4.12 · (√h₁ + √h₂)
```

而 `4.12` 這個常數本身就是 `√(2·k·Re)/1000 = 4.1218`。

**這條性質已用單元測試驗證**（`packages/engine/test/mva.test.ts`），實測結果：

| 雷達高 | 目標高 | MVA 場計算 | 4.12 公式 | 相對誤差 |
|---|---|---|---|---|
| 30 m | 100 m | 63.70 km | 63.77 km | 0.10% |
| 30 m | 1000 m | 152.90 km | 152.85 km | 0.03% |
| 10 m | 100 m | 54.20 km | 54.23 km | 0.05% |
| 100 m | 5000 m | 332.60 km | 332.53 km | 0.02% |
| 500 m | 10000 m | 504.30 km | 504.13 km | 0.04% |

也就是說：**不需要在程式裡另外寫一條地平線公式**。它是 MVA 引擎在平坦地形下的特例。
少一條公式，就少一處會不一致的地方。

### 3.3 為什麼這是整個架構的樞紐

MVA 場算完之後，**每個高度切片都只是一次逐點比較**：

```
可視(φ, r, h)  ⟺  h ≥ MVA(φ, r)
```

高度滑桿因此是零成本的 —— 把 MVA 場上傳成一張紋理，切片判斷寫在 fragment shader 裡，
拉滑桿 60 fps。原構想中被切成 Phase 2（高度）與 Phase 3（地形）的兩件事，在這裡是同一件事。

### 3.4 效能實測

在 Node（單執行緒、無 SIMD）上量測，同一份程式碼在 Web Worker 中的表現應相當：

| 項目 | 數值 |
|---|---|
| 720 方位 × 500 距離箱（100 km，200 m 解析度） | **22.8 ms** |
| 場大小（float32） | 1.37 MB |
| 場大小（uint16 公尺量化） | 0.69 MB |

結論：**拖曳陣地即時重算完全可行**，20 個陣地全部重算也在半秒內。
原構想「viewshed 不能在瀏覽器算」的假設，在 90 m DEM 這個解析度上不成立。

（30 m DEM 全島 4000×4900 以上、資料量約 9 倍，仍可行但下載成本高；
建議互動用 90 m，需要精算時再走離線批次路徑，見 §9。）

### 3.5 地形遮蔽的量級

一個示範測試：東方 20 km 處放一道 1500 m 的牆（粗略模擬中央山脈），
天線架高 30 m，看 60 km 處的最低可視高度：

- 正東（山後）：**4792 m**
- 正西（開闊）：**82 m**

同一部雷達，東西向低空涵蓋差 **58 倍**。這就是為什麼「畫一個圓」在台灣特別離譜。

## 4. 可接戰判定：完整條件鏈

點 `P`（方位 φ、距離 r、高度 h）能被陣地 `B` 對威脅 `T` 接戰，需同時滿足：

**A. 偵獲** — 存在同一 C2 群組內的感測器 `S`：

1. `h ≥ MVA_S(φ_S, r_S)` — 地形 / 曲率 LOS
2. `r_S ≤ R_det(S, RCS_T)`，其中 `R_det = R_ref · (RCS_T / RCS_ref)^(1/4)` — 雷達方程的四次方根律
3. 仰角在 `S` 的掃描界限內 — **上界會在陣地正上方造成「靜默錐」**，地圖上是一個真實可見的空洞
4. 方位在 `S` 的掃描扇區內

**B. 運動學可及**：

5. `R_min(h) ≤ r_B ≤ R_max(h) · aspect_factor` — 由 `kinematics.envelope` 內插
6. `h` 在 `alt_limits` 之內
7. 方位在發射器扇區遮罩內

**C. 導引 LOS**：

8. 若 `guidance.requires_illumination`（SARH / CLOS / 光學砲瞄）：需**全程** `h ≥ MVA_B`
9. 若 `guidance.uplink_required`：需發射瞬間至中途的資料鏈 LOS
10. 主動雷達導引（`active_rf`）可放寬為僅需發射點 LOS

**D. 時間可行**（僅動態模式）：

11. `T_window ≥ t_reaction + t_flyout`
12. 通道與待發彈未耗盡

條件 C 是原構想完全沒有的一層，而它產生的差異很大：
主動導引的天弓三型可以打自己看不到的目標（靠外部供軌），
但 35 快砲必須自己看得見。同一個地形、同一個高度，兩者的涵蓋圖形狀完全不同 ——
**這正是最值得被畫出來的東西**。

## 5. 資料模型

### 5.1 不確定度是型別，不是註解

所有物理量一律用 `Estimate` 結構，禁止裸數字：

```jsonc
{ "min": 15, "nominal": 25, "max": 40, "confidence": "low", "sources": ["iiss-2025-p42"] }
```

UI 全域切換 保守 / 標稱 / 樂觀，直接讀 `min` / `nominal` / `max`。
另有「顯示不確定度」模式：涵蓋邊界畫成一條**帶**（min 與 max 兩條等值線之間填色），
而不是一條假裝很精確的線。

`confidence: "low"` 的欄位在 UI 上以虛線邊界呈現。沒有 `sources` 的欄位不得標為 `high`。

**資料撰寫鐵律：不得雙重扣減。** `kinematics.envelope` 只能寫**純運動學**可及距離
（飛彈靠自身能量在該高度能飛多遠）。偵測、地平線、地形限制一律不准寫進這張表 ——
那些由 §4 的條件鏈另外扣。

這條規則是踩過坑之後補的：初版 tk3.json 在 100 m 高度寫了 25 km，
那其實是把地平線限制偷偷算進運動學表裡。結果是同一個限制被扣兩次，
而且 UI 會錯誤地告訴使用者「限制因素是運動學」——
正好掩蓋掉這個工具最想講的那件事。修正後低空純運動學值改為 70 km，
地平線（52.9 km）才如實成為限制因素。

Schema 定義：[`data/schema/system.schema.json`](../data/schema/system.schema.json)
範例：[`tk3.json`](../data/systems/tk3.json)（高層）、
[`sw2-land.json`](../data/systems/sw2-land.json)（短程）、
[`gun35.json`](../data/systems/gun35.json)（點防禦）

### 5.2 實體

```
System   武器系統型別（靜態目錄，每型一檔）
Sensor   感測器型別（可獨立於發射器存在）
Site     陣地實例：座標 + System id + 狀態 + 扇區限制 + 彈藥狀態
C2Group  資料鏈群組：哪些 Sensor 供軌給哪些 Site。感測器—射手分離在此生效
Threat   威脅：航跡點列 + RCS + 速度 + 型別 + 終端機動旗標
Scenario 想定：Site 集合 + C2Group + Threat 集合 + 環境參數（k factor）
```

`Scenario` 就是一個 JSON，可匯出匯入。這是專案的存檔格式，也是回歸測試的輸入。

### 5.3 分層目錄

| 層級 | 系統 | 色相 | 狀態 |
|---|---|---|---|
| 高層／反彈道 | 天弓三型、愛國者三型（PAC-3） | 藍 210 / 紫藍 255 | ✅ 已收錄 |
| 區域中高層 | 愛國者二型（PAC-2 GEM）、天弓一型、天弓二型、標準二型（艦載） | 綠 140 / 168 / 178 / 225 | ✅ 已收錄 |
| 中短程 | 陸射劍二、海劍二（艦載） | 黃 50 / 65 | ✅ 已收錄 |
| 極短程／點防禦 | 35 快砲（天兵）、方陣快砲（陸基）、復仇者飛彈車、單兵刺針 | 紅 0 / 340 / 30 / 15 | ✅ 已收錄 |

四個層級都至少有一筆資料了。同一層內色相刻意錯開（例如天弓一/二型與愛國者二型都是「區域中高層」但色相不同），涵蓋圖疊在一起時才分得出是哪一套系統畫的。

**愛國者兩型、天弓一/二/三型、陸射劍二與海劍二都刻意拆成多筆資料，不合併**：同一系列不同世代/不同載台的性能、導引方式、彈藥計數方式經常完全不同（PAC-2 是 TVM 需要地面雷達全程追蹤，PAC-3 是主動雷達尋標命中即摧毀；陸射劍二拿掉了艦射型的助推器，射程差一倍）——合併成一筆會是本專案在 §1 已經批評過的同一種錯誤（把不同性質的量硬湊成一個數字）。共用同一套雷達的系列（如愛國者兩型）則刻意讓 `channels`／`r_det_ref_km` 兩個欄位給相同的數字與理由，反映火力單元層級的限制不因飛彈種類而變。

**`sensor: null` 的第一個實例**：單兵刺針（`stinger.json`）沒有自己的雷達，`sensor` 欄位直接設成 `null`——這是引擎架構原本就支援、但前七筆系統資料都沒有用到的分支（`sensorsFor` 在『各自為政』C2 模式下會讓沒有 sensor 的陣地拿到空的感測器清單，永遠偵獲不到任何目標）。刺針因此變成感測器—射手分離（§4）最直接的教材：同一枚飛彈，切到『全島共享軌跡』就能靠其他陣地供軌接戰，切回『各自為政』就完全打不到，兩種模式的差異在這個系統上比在有機載雷達的系統上更極端、更容易看懂。

**陸基方陣快砲是目前唯一一筆刻意標註『非普遍部署』的系統**：台灣現況是一具海軍除役艦艇拆下、移交空軍駐防單一雷達站的個案，不是制式陸基型號（見 `sources.json` 的 `twz-taiwan-land-phalanx`）。收錄它代表的是 §12.3 講的「如果這樣部署會怎樣」的推理用途，不是宣稱陸基方陣已經普遍存在——這跟其他系統的差別，在於它連『存在但參數不確定』都算樂觀，是『目前幾乎不存在，但拿來想像很有用』。

**兩個新增系統暴露的既有限制，記在這裡而不是假裝不存在**：
1. **飛彈助推段未建模**（`timeline.ts` 假設 #2）：接戰時間軸把飛彈當成從發射瞬間就以「平均速度」直線飛行，不模擬助推段的加速過程。對天弓三型這種 200 km 級的長程接戰，助推的幾秒鐘占飛行時間的比例小，影響可忽略；但對愛國者、刺針、復仇者這類近距攔截（PAC-3 對彈道飛彈的攔截距離公開數字只有 35 km，刺針只有個位數公里），助推段占比會變得不可忽略，目前的等速假設在那種情況下會系統性高估飛彈初期的位置、進而低估實際攔截時間。
2. **雷達方位扇區未建模**：愛國者的 AN/MPQ-53 相位陣列雷達實際上只有 120° 涵蓋扇區（見 `sources.json` 的 `search-mpq53-sector`），需朝向預期威脅方向部署，不像天弓三型那樣可視為全周界。系統目錄的 `azimuth_mask_deg` 是相對真北的固定角度，而 `Site` 資料模型目前沒有「雷達朝向」欄位——同一個絕對角度套用在不同座標的陣地上會代表不同的實際朝向，套錯比不套更危險。因此愛國者兩筆資料都刻意把 `azimuth_mask_deg` 留空（視為全周界），涵蓋圖因此對愛國者是**過度樂觀**的。要修正需要先幫 `Site` 加一個朝向欄位，這是尚未排入的資料模型工作。
3. **艦載系統沒有『艦體朝向』或『航行』的概念**：`platform: "naval"` 純粹是標籤，Site 模型仍然只有經緯度——把標準二型或海劍二放到海面上，涵蓋圖會把它當成一個永遠靜止、面向四面八方的陣地。真實軍艦會移動、桅杆會被自己的上層結構局部遮蔽，這兩者都沒有建模，跟陸基系統一視同仁地套用同一套地形/曲率鏈。

### 5.4 具名威脅

`data/threats.json` 除了原有六個通用類別，新增了三個具名、公開已知型號：**鷹擊-12**（超音速掠海反艦飛彈，本專案第一個超音速威脅，用來示範反應時間如何被壓縮到接近極限）、**殲-20**（匿蹤戰機，RCS 區間刻意比通用『低可偵測性戰機』類別更寬，反映其前向優先、非全向匿蹤的設計取捨）、**東風-15**（短程彈道飛彈，`typical_altitude_m` 刻意取再入終端窗口 20 km 而非彈道頂點 100 km——後者會讓預設航跡超出目錄中每一套系統的 `alt_limits.max_km`，變成『預設無法示範』，見 `threats.json` 該筆的 note）。

具名威脅與通用類別並存，不是取代關係：通用類別代表『這一整類威脅大概是什麼量級』，具名威脅代表『如果來的剛好是這一型，會怎樣』——兩種問題都有人會問，答案通常不一樣。

## 6. 三個主要輸出

### 6.1 高度切片涵蓋圖（主視圖）

底部滑桿 0–20 km（對數刻度，因為 0–1 km 的變化最劇烈）。
圖層互斥切換，避免視覺糊團：

1. 雷達偵測涵蓋
2. 攔截包絡
3. **縱深熱圖** — 每格被幾套系統涵蓋
4. 地形遮蔽（MVA 場本身，用色階顯示「這裡至少要飛多高才會被看到」）

縱深熱圖必須是**威脅條件化**的：對 RCS 0.1 m² 的巡弋飛彈與 RCS 5 m² 的戰機，
同一組陣地的縱深圖完全不同。兩套系統都看不到低空時，重疊層數是 0 而不是 2。

### 6.2 垂直剖面圖（第二主打）

在地圖上畫一條線 → 產生側視圖：地形剖面 + 每套系統的包絡上下界 + 偵測門檻。
低空走廊在這張圖上是**一條看得見的縫**。

成本極低：500 距離 × 200 高度 = 10 萬次判定，即時。
資訊密度遠高於 3D 包絡體，這也是本設計不推 Cesium 的主因。

### 6.3 接戰時間軸

給一條威脅航跡，輸出甘特圖式的時間軸。一列＝航跡上的一個架次，橫軸＝時間，
每列上看得到：何時被偵獲（豎線）、每一次發射到攔截的飛行段（依射手著色）、
以及沒被打到的那些卡在哪一關（列底色）。

這張圖回答的是前兩個輸出問不到的問題：涵蓋圖說「這裡打得到」，
時間軸說「同時來三十個的時候，打得到有什麼用」。

輸出的是**射擊機會**而不是擊殺數 —— 理由見 §10 的 Phase 4，
那是本專案最重要的一個「刻意不算」的決定。

漏網原因分成五類，因為它們指向完全不同的補救方向：
**從未偵獲**（要加感測器，加射手沒用）、**通道飽和**（要加射控通道）、
**待發彈耗盡**（要加彈）、**反應不及**（要加預警時間）、
**不在接戰包絡內**（射程／地形／高度限制）。
把這五種混成一句「沒打到」，等於什麼都沒說。

## 7. 座標與投影

**不投影。** 所有幾何用「起點 + 方位角 + 大地線距離」表達，實作見
[`packages/engine/src/geodesy.ts`](../packages/engine/src/geodesy.ts)。

精度做法：球面公式，但半徑取「該緯度、該方位角上的歐拉曲率半徑」
`R(φ,α) = 1 / (cos²α/M + sin²α/N)`。這讓 100 km 內誤差降到約 10 m 量級，程式碼只多五行。

涵蓋多邊形由 `geodesicRing(center, radii[])` 產生，每個方位角可有不同半徑 ——
這正是表達地形遮蔽鋸齒邊界所需要的。

需要 raster 運算時（例如縱深熱圖聚合），才臨時投到**以該陣地為中心的方位等距投影**，
用完丟棄。不維護任何全域投影狀態。

## 8. 技術選型

| 層 | 選擇 | 理由 |
|---|---|---|
| 建置 | Vite + TypeScript | — |
| 地圖 | MapLibre GL JS | 開源、可插自訂 WebGL2 圖層 |
| 涵蓋渲染 | 自訂 MapLibre CustomLayer（原生 WebGL2） | MVA 場當紋理，高度切片判定寫在 fragment shader，滑桿 60 fps |
| 計算 | Web Worker + Comlink | MVA 場計算不阻塞 UI |
| 狀態 | Zustand | Scenario 即 store，序列化直接就是存檔 |
| 測試 | Vitest | 引擎全部純函式，無 DOM 依賴 |
| DEM 前處理 | Python + rasterio（`tools/`） | 一次性：SRTM/DTM → Terrain-RGB PNG 磚 |
| 後端 | **無** | v1 完全靜態，可部署到任何 CDN |

### 反對 CesiumJS

原構想推薦 Cesium。三個理由不採用：

1. **視覺失效**：多個半透明 3D 包絡體疊起來會糊成一團，看不出縱深。這是 3D 防空視覺化的通病。
2. **打架成本**：我們要做的是自訂 raster 數學（MVA 紋理查表），Cesium 的抽象層會一路擋。
3. **它解的問題我們不需要**：全球地形串流，但我們只關心台灣周邊 3.5° × 4.0°，自己準備一份就好。

3D 只做一件事：**垂直剖面**。而剖面圖用 2D canvas 畫就夠了。

### 架構原則：引擎必須是純的

```
packages/engine/    純 TypeScript，零 DOM 依賴，全部單元測試
packages/app/       React + MapLibre，只負責渲染與互動
tools/              Python DEM 前處理與離線批次分析
data/               系統目錄、想定、來源書目
docs/
```

引擎為純函式庫的直接好處：**同一份程式碼可以在 Node 裡跑批次分析**
（例如掃描一萬個候選陣地位置，找出補洞效益最大的那個），而不用開瀏覽器。

### Phase 3 修正的一個真實錯誤：MVA 場邊界

垂直剖面圖一畫出來就暴露了一個 Phase 2 沒發現的問題：
中央山脈背後、超出 MVA 場計算半徑（120 km）的低空格點被判為「已偵獲」。

原因是場外退回平坦地形地平線，等於**假裝山消失了**。
正確做法是外推邊界射線 —— θmax 沿射線單調不減，所以場邊界上的 θmax
對更遠處仍然成立（只會低估遮蔽，不會高估）：

```
tan(θedge) = (MVA(extent) − h_site − c(extent)) / extent
MVA(r)     = h_site + r·tan(θedge) + c(r)        r > extent
```

實作為 `extrapolatedMvaAt()`，涵蓋計算與接戰判定都改用它。
修正後同一條剖面線上，山背後的區域由「已偵獲但無射手」變成正確的「未偵獲」。

這說明了為什麼垂直剖面圖值得早做：它讓 3D 空間中的錯誤變成平面上一眼可見的色塊。

#### Phase 4 最重要的設計決定：不算擊殺機率

最容易被期待的輸出是「打不打得下來」。本專案**不產生**這個數字。

它需要 Pk（單發擊殺率），而 Pk 是各國最保護的參數之一，公開來源全是猜的，
且對目標型別、接戰幾何、電子作戰環境極度敏感。用一個捏造的 Pk 乘上去，
只會把「猜測」包裝成「戰損評估」—— 那正是 §12 第 1 條要避免的事。

輸出的是**射擊機會**：目標抵達其目標區之前，防空網總共能發射幾次、
在哪個距離發射、哪些目標一次都沒被打到、以及卡在哪一關。
這些全部由幾何與時序決定，用的都是已經在 `data/` 裡、標好不確定度的參數。

飽和分析在這個框架下依然完整成立：三十個目標同時進入、全網總通道十七，
十八個一次都輪不到 —— 這個結論不需要知道 Pk。

#### 明確列出的模擬假設

這五條全部寫在 `timeline.ts` 的檔頭，其中兩條在 UI 上可調：

1. **一有機會就打**。結果因此是射擊機會的**上界**，對防守方樂觀。
2. **飛彈直線等速**飛向攔截點，速度取 `avg_missile_speed_mps`。不模擬助推／滑翔段。
3. **攔截點必須合法**：攔截時刻該點要通過完整接戰條件鏈，且 C2 群組仍維持接觸
   —— 目標飛進地形陰影，中途指令就斷了。
4. **射擊優先序**：多目標競爭通道時，先打距離其目標區剩餘時間最短的。這是準則假設，不是物理。
5. **每個射手對同一目標的接戰次數有上限**（UI 可調，預設 2）。不設上限的話，
   單一射手會對同一目標無限重複開火，飽和分析就失去意義。

#### 兩個被 Phase 4 逼出來的資料模型缺口

**火砲的「彈」不是飛彈的「彈」。** 35 快砲的 `ready_rounds` 是 238 **發**，
若直接當成 238 次接戰機會，快砲在飽和分析裡會變成幾乎無限的彈藥。
新增 `rounds_per_engagement`（砲為一次連射的發數，飛彈為 1），
238 發因此換算成約 7 次接戰。

**`ready_rounds` 描述的是單一發射單元，不是一個陣地。** 這一點 `tk3.json`
的註解本來就寫著「每發射箱；一個連的總數需在陣地層級設定」，而第一版模擬直接
拿它當陣地彈量，結果十二個目標裡有八個被判成「待發彈耗盡」—— 一個純粹由
資料模型缺口造成的假結論。一個連有幾具發射架是**編制**問題，不是武器性能，
不該寫進系統目錄，所以改成陣地層級的 `readyRoundsOverride`。

總射擊次數完全相同（彈量封頂），但**一發一目標**的分配方式讓未被接戰的目標
從 18 降到 6。這裡必須說清楚：這**不代表**射一發比較好 ——
那要比較 `Pk` 與 `1−(1−Pk)²`，而 Pk 正是本工具拒絕捏造的數字。
工具能做的是把這個取捨變成兩個可以看見的數字，決定權留給使用者。

上限 3 與上限 2 結果相同，因為彈量在第三次接戰前就見底了。

## 10.5 踩過的坑（渲染層）

以下三個都造成同一個症狀：**畫面上一坨黑塊**。三個成因完全不同，
而且三個都不是計算錯誤 —— 數值一路都是對的，壞的是幾何合法性與渲染管線。

### 坑 1：把「被遮蔽的方位」畫成半徑 0 的頂點

地形把部分方位完全遮蔽時，涵蓋多邊形的外環與最小射程的洞各會有數百個點
塌在陣地中心（實測 720 個方位中有 275 個）。這是自相交的退化多邊形，
MapLibre 三角化後吐出大量重疊三角形，每個都疊一次 `fill-opacity`，
疊二十層就從半透明藍變成不透明深色。

**正解**：被完全遮蔽的扇區是**不存在的區域**，不是半徑為零的區域。
按連續可視方位切成數個扇形多邊形（MultiPolygon），每個扇形 = 外弧 + 反向內弧，
必然是簡單多邊形。回歸測試見 `packages/app/test/coverageGeometry.test.ts`，
守衛條件是「落在陣地中心 100 m 內的頂點數必須為 0」。

### 坑 2：MapLibre 畫布尺寸沒跟上容器

實測容器是 720×577，但 MapLibre 內部畫布卡在預設的 400×24，
CSS 再把 24 px 高的內容拉伸到 577 px —— 整張地圖變成一條糊掉的色帶。

成因是建構當下容器還沒拿到樣式（Vite 在 dev 模式非同步注入 CSS），
之後沒有任何事件把它救回來。

**正解**：自己觀察容器並呼叫 `map.resize()`，不要只依賴 `trackResize`。
另外，垂直剖面面板開合會讓地圖高度變動 240 px，那是**我們自己控制的狀態**，
直接在對應的 effect 裡明確 resize，不要依賴 ResizeObserver ——
它的回呼綁在畫面更新生命週期上，不保證即時。

### 坑 3：MapLibre 的 `canvas` 來源上傳全黑材質

縱深熱圖與地形遮蔽圖層原本用 `type: 'canvas'` 來源直接餵 canvas，結果整個圖層是純黑矩形。

最小對照實驗：

| 測試 | 畫面實際像素 |
|---|---|
| 純紅 canvas → `type: 'canvas'` 來源 | `17,19,21`（黑） |
| 同一張 canvas → `toDataURL` → `type: 'image'` 來源 | `246,19,21`（紅） |

**正解**：改用 `image` 來源。編碼成本 512×512 約 32 ms，
相對於熱圖本身 30–150 ms 的計算量可以接受，而且 image 來源的生命週期單純得多
（不必煩惱何時重傳材質）。

### 坑 4：2D canvas 的繪圖緩衝區停在舊尺寸（坑 2 的變形）

Phase 4 的時間軸面板一畫出來就中了同一個問題的 2D 版本：
繪製 effect 依賴的是**資料**，不是尺寸，所以視窗變大之後 `canvas.width`
還停在舊值。實測 755×185 的元素上掛著 652×237 的緩衝區 ——
內容被 CSS 拉伸成錯誤的長寬比。垂直剖面圖有同一個潛在問題，一併修掉。

**正解**：`useCanvasSize()`（[`useCanvasSize.ts`](../packages/app/src/analysis/useCanvasSize.ts)）
回傳一個尺寸變更計數器，放進繪製 effect 的相依陣列。
同時掛 ResizeObserver 與 `window.resize`，靠尺寸字串去重 ——
理由同坑 2：ResizeObserver 的回呼不保證即時。

### 這四個坑的共同教訓

它們都無法用單元測試抓到，也都不會讓任何數值出錯。診斷方法是**直接量測渲染結果**：

```js
// WebGL（地圖圖層）
map._render(performance.now());
gl.readPixels(x, y, 1, 1, gl.RGBA, gl.UNSIGNED_BYTE, buf);

// 2D canvas（剖面、時間軸）
ctx.getImageData(0, 0, canvas.width, canvas.height);
```

在無法截圖的環境下，讀回像素是唯一能證明「畫出來的東西是對的」的手段。
實務上最有效的兩個檢查是：**統計整張畫布的相異顏色數**（全黑、空白、
只有底圖都會立刻現形），以及**把已知圖徵的經緯度投影成像素座標後就地取樣**
（能證明「那條藍線真的是飛彈」，而不只是「畫面上有藍色」）。
坑 1 則是靠量測「有幾個頂點塌在同一點」抓到的，坑 4 是靠比對緩衝區與 CSS 尺寸。

數值正確不等於畫面正確，這兩件事要分開驗。

## 11. 驗證策略

引擎正確性不能靠「看起來合理」。三層把關：

1. **解析解測試**：平坦地形必須還原 4.12 公式（已通過，§3.2）；
   單牆地形的遮蔽射線必須落在幾何上下界之間（已通過）
2. **不變量測試**：平坦地形上 MVA 對距離單調遞增；旋轉對稱；
   `k` 增大時涵蓋必然擴大；解析度加倍時結果收斂
3. **回歸想定**：把幾個 `Scenario` JSON 存成黃金檔，輸出的涵蓋面積 / 縱深統計不得無故變動

**不做**的驗證：拿真實部署去對答案。我們沒有真值，假裝有反而危險。

## 12. 誠實性原則

這一節是設計的一部分，不是免責聲明。

1. **所有數字都是公開推估**，不確定度大到不能忽略。UI 常駐可見的提示，不是藏在 About 頁。
2. **參數只存在 `data/`**，程式碼中不得出現硬編碼的性能數字。整份參數集可被第三方審查與替換。
3. **預設想定的陣地位置為假想示例**，用途是演示分層防空的概念。
   工具的價值在於「如果這樣部署會怎樣」的推理，而不是宣稱任何實際部署。
4. **不確定度要看得見**：能畫成帶就不畫成線，`confidence: low` 的邊界用虛線。
5. **來源可追**：`data/sources.json` 是書目，每個 `Estimate.sources` 指向它。
   `packages/engine/test/sources.test.ts` 會擋下失效的參照，以及「標了 medium/high
   卻既無來源也無理由說明」的欄位——防止書目與系統檔各自漂移而沒人發現。

   截至 2026-08，已補上公開來源的欄位：天弓三型的高空射程 200 km（三個獨立媒體來源互相
   印證，confidence 升為 medium）與高度上限 45 km（官方宣稱值，但同一份來源也引述
   《自由時報》報導的『有效攔截高度』僅 24–26 km，這個落差刻意保留在 note 裡，不是
   挑對自己有利的那個數字）；35 快砲的射程／射高／雷達距離／砲口初速（Oerlikon GDF
   規格書等級數字，是目前唯一一個 `confidence: high` 的速度欄位）；陸射劍二的陸射型
   射程 15 km（單一媒體轉述，confidence 仍為 low）；三個威脅類別的 RCS 量級
   （攻擊機、低可偵測性戰機、巡弋飛彈——後者的來源本身就互相矛盾，這矛盾被寫進了 note）。

   **仍然沒有、以後大概也不會有公開來源的欄位**：反應時間、通道數、精確雷達偵測距離、
   陣地層級待發彈量。這些是各國最不願公開的作戰參數，找不到來源不是本專案偷懶，
   是誠實地承認這類數字本來就不該有『查得到的標準答案』——待發彈量因此設計成
   使用者在 UI 自行輸入（`readyRoundsOverride`），而不是假裝系統目錄裡有一個正確值。
